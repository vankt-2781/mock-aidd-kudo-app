## Authorization System Type

**System Type**: rbac (two ordinary groups plus one admin role), with a time-based launch gate and ownership rules on the Kudos board (a sender cannot like their own kudos; personal stats belong to their owner; a sender cannot send a kudos to themselves; the sender of an anonymous kudos is hidden from every public surface)

**Identified Roles**:
- Visitor (not signed in)
- Signed-in user (verified Google account via Supabase)
- Admin (signed-in user whose Supabase account metadata marks the role as admin)

## Curated View

- **Before the launch time**
  - **Visitor** and **signed-in user** are sent to the Countdown page when they open any page other than the Countdown page, the login page, the sign-in return step, the API routes and static files. They can still open the login page, and the Countdown page itself.
  - **Admin** browses the whole site normally, exactly as after launch.
- **From the launch time on** the gate is gone. All groups get the access described below, and the Countdown page sends everyone to the homepage.
- **Visitor** can open the homepage, the Awards page, the Kudos board and the login page, and switch the language. On the Kudos board a visitor can read everything public: banner, highlight carousel, filters, spotlight (hover, pan, zoom, search), feed, thumbnails in full size, the gift list, and copy a kudos link. "Mở quà" is visible to visitors but goes to login. A visitor cannot like or unlike, use the input pill to compose a kudos, press "Mở quà", or open a kudos detail or a person's profile: each of these sends the visitor to the login page (carrying a return-to path back to the board), with no change made. A visitor sees no personal stats, no notification bell and no account menu. Visitor cannot open the Todo page.
- **Signed-in user** can do everything a visitor can, plus see the notification bell (empty, no badge for now), open the account menu (Profile, Sign out), open the Todo page, and on the Kudos board: like and unlike other people's kudos, see their own personal stats (kudos received and sent, hearts received, Secret Boxes opened and unopened), use the input pill to open the Viết Kudo dialog and send a kudos (to anyone except themselves, optionally anonymously, with up to 5 jpg or png images of at most 5 MB each uploaded to their own storage folder), use "Mở quà" (opens the Secret Box modal), open kudos details (placeholder), and open Profile pages: their own (hero, badges, counters, Received and Sent feeds, including their own anonymous kudos with the real name) and other Sunners' (hero, badges, Received kudos only, no counts; a bar opens the Viết Kudo dialog with that person preselected). A visitor opening `/profile` is sent to `/login?next=%2Fprofile`. A signed-in user with at least one unopened Secret Box can open it from the "Mở Secret Box" button in the Kudos board sidebar or on their own Profile. Each open reveals one badge, chosen by the server, and unlocks the matching slot in their own Profile badge collection. A visitor clicking that button on the Kudos board is sent to login (no change made). Other users' boxes and badges are never readable or openable. A signed-in user who opens the login page is sent to Todo.
- **Sender of a kudos** (a signed-in user looking at a kudos they wrote) cannot like it: the heart is disabled and the server refuses it. This also holds for an anonymous kudos: the sender still sees a disabled heart, decided by a server-side flag computed from their own session, not by any public sender field.
- **Anonymous kudos**: any viewer, including the recipient and the sender's colleagues, sees only the alias (the name the sender typed, or "Ẩn danh") and the default avatar; no sender name, avatar, department, stars, profile link or id is returned by any public read path.
- **Admin** can do everything a signed-in user can, also sees Admin Dashboard in the account menu, and is the group meant to configure special days (double hearts) once an admin screen exists; for now special days are seeded data.
- All groups can switch the language. It changes wording only.

## Access Boundaries

Before launch, the line between admin and everyone else decides whether the site is browsable at all: only admins pass the launch gate. After launch the homepage and the Kudos board are public: no sign-in is needed to read them, and being signed in does not redirect away from them. The line between visitor and signed-in user decides whether the bell, account menu, personal stats and every Kudos interaction are available. The line between signed-in user and admin decides whether Admin Dashboard appears.

Kudos data rules, enforced in the database as well as in the interface: everyone may read the kudos domain data (people, departments, hashtags, kudos, likes, gift events, special days); only a signed-in user may add or remove a like, only as themselves, only on a kudos they did not send, and at most one like per user per kudos. A signed-in user can write a kudos only through the send function, and only as themselves: the sender is taken from the verified session on the server, the recipient must be an existing person other than the sender, 1 to 5 hashtags are required (new hashtags are created by that same function), and at most 5 images are accepted, each an image address in the project's own bucket (at most 500 characters) that the same user reserved earlier through the reservation function; the submitted rich-text body is capped at 50,000 characters. Nobody can write hashtags, kudos links, events or special days any other way (gift events and special days stay seeded). Image storage: anyone can read uploaded images (public bucket); only a signed-in user can upload, only to a path they first reserved through a reservation function (limit 25 reservations per user per hour), only jpg or png, at most 5 MB each; visitors cannot upload. Stored paths are random and carry no account identity, because anonymous kudos publish these addresses; the link from path to uploader lives in a registry table that clients cannot read or write (only the send and reservation functions touch it). For anonymous kudos the sender identity is withheld from visitors and signed-in users alike on every public surface (cards, highlights, spotlight, public stats, direct view or table queries); the database keeps the sender for accountability (direct select of the sender column is revoked from visitors and signed-in users; reads go through masked views) but exposes it only to database administrators, and no admin screen reads it yet. Personal stats are computed only for the signed-in viewer's own profile and never for anyone else; Secret Box counts are readable only by their owner (signed-in only; visitors have no access). The link from a profile to its sign-in account (`auth_user_id`) is hidden from visitors and signed-in users alike; a signed-in user reads their own full profile through a dedicated own-row view.

Profile rules, enforced in the database as well as in the interface: the Profile page is signed-in-only — a visitor opening `/profile` (with or without a person id) is sent to login with a return-to back to plain `/profile` (the allow-list stays exact-match; `/profile?id=...` is ignored, no open redirect). Which face renders — own or someone else's — is decided on the server from the verified session and the requested id, never from anything the browser claims. The person id is untrusted: shape-checked before any query; malformed, unknown or repeated ids all give the same not-found page. On another person's profile the viewer sees the hero, icon collection and Received list only — no sent list, sent label, sent count, received count, personal stats or Secret Box data. The viewer's own Sent list (which includes their anonymous kudos, shown with their real name and an "Ẩn danh" chip) is served only by the `own_sent_kudos` security-definer view: it restricts every row to the caller's own profile via the verified session, is granted to signed-in users only, and a Sent request for anyone but the caller is refused by the server action as well. Anonymous kudos stay masked on every Received list, including the recipient's own. The page is read-only: no email, account id or anonymous sender id is placed in the payload.

Secret Box rules, enforced in the database as well as in the interface: opening a box is possible only through the `open_secret_box` function, which takes no input and works on the caller only: the profile is derived from the verified session, never from anything the browser sends. The function claims exactly one of the caller's own unopened boxes (concurrent calls cannot claim the same box), picks the badge by a server-side weighted random draw (Stay Gold 30%, Flow to Horizon 25%, Beyond the Boundary 10%, Root Further 5%, Touch of Light 20%, Revival 10%), records the open time and the badge, and returns the badge and the caller's remaining unopened count. It is executable by signed-in users only (visitors are refused); when the caller has no unopened box it refuses with a controlled error and changes nothing. The `badge` column on `secret_boxes` is empty for unopened boxes (and for boxes opened before this feature), accepts only the six known badge keys, and is readable only by the box owner through the existing owner-only select; no client has any insert, update or delete right on `secret_boxes`, so a badge cannot be set, changed, rerolled or read for someone else from the browser. A Sunner's badge collection unlocks from their own opened boxes only; another Sunner's Profile carries no badge or Secret Box data (resolved: badges are visible to the owner only).

The admin marker lives in the Supabase account metadata that users cannot edit themselves; it is set by the team (Supabase Studio or admin API). The launch gate reads it from the verified session, never from user-editable profile data. Hiding the menu item only guides the interface; the Admin Dashboard page itself must also refuse non-admins on the server (route details TBD). Only Admin Dashboard is still a placeholder page; Profile is a real page (F008).

Everything under Todo still needs a signed-in user. Login is for visitors only. If the sign-in service cannot be reached, the user is treated as a visitor, so access is denied rather than granted: on the Kudos board this means gated actions send the user to login, and before launch the user is held on the Countdown page. Sign out is available from the homepage account menu as well as the Todo page, using the same existing action.

The launch time is a deploy-time server setting, readable by anyone through a public configuration route that returns only the start time. It carries no secret and grants no access.

## Special Conditions

- The sign-in return step (after Google) is open to everyone, before and after launch. It sends the user to Todo by default, or to a return-to path when the login link carries one that is an exact member of a small internal allow-list (at least the Kudos board). Anything else (missing, external, malformed) is ignored and the user lands on Todo, so no open redirect is possible. A visitor redirected from a gated Kudos action therefore comes back to the board after signing in.
- The login page stays reachable before launch so admins can sign in and users with an expired session are not stuck.
- The launch gate is checked first. Before launch, a non-admin outside the excluded pages goes to the Countdown page before any other rule applies. After launch the existing login and Todo rules behave exactly as before; the Kudos board adds no route-level guard, only per-action gating.
- An invalid or missing launch time means "no gate" (treated as already launched), so a misconfiguration cannot lock the whole site out.
- A profile record is created automatically on a user's first sign-in, so a new user can like and see stats at once.
- The identity used for a like or a sent kudos comes from the verified session on the server, never from anything the browser sends.
- Content typed in the editor is untrusted: the server strips everything outside an allow-list (basic formatting, safe http, https and mailto links, mention spans; no `class` or inline styles) before it is stored. The database function can also be called directly, so stored HTML is still treated as untrusted and the board renders the plain-text copy.
- Image addresses submitted with a kudos are accepted only when they start with the configured storage origin (`app_settings.storage_public_base`, set per environment), match the random `<uuid>/<uuid>.<jpg|jpeg|png>` path shape, and were reserved by the sender. A foreign host or another user's reserved path is refused.
- Mentions are styled text only: they grant no access and send no notification.
- Hiding anonymity must not leak through side channels: the public per-person "kudos sent" total counts non-anonymous kudos only, while a signed-in user's own sidebar total counts everything they sent (owner-only query).
- A guest who clicks the compose pill is sent to the login page with a return-to path back to the board and no dialog opens.
- Unliking revokes exactly the hearts that like awarded (1 or 2), whatever the special-day setting is later.
- The badge outcome of a Secret Box open is decided and stored by the database function in one step; the client only displays the returned result and any displayed count always comes from the backend, so repeating, racing or forging requests cannot change odds or add opens.
- Language choice is a cookie preference and does not affect access.
- A user whose admin marker is missing or has any other value is treated as a regular signed-in user.

No feature flags or experiments identified.
